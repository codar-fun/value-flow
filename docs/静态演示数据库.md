# 流动圈静态演示数据库

> 状态：开发交接版 v0.1
>
> 日期：2026-07-15
>
> 代码事实来源：`../app/demo-data.ts`
> 用途：为静态 Demo 提供统一、可追溯的虚构数据，不代表真实用户或真实后端方案。

## 1. 使用原则

- 页面不再分别手写成员摘要、动态文案和个人页数字；成员、圈子账户、需要/提供、好人卡与交易都从同一份数据读取。
- 本文件用于产品和开发交接；`app/demo-data.ts` 是当前运行中的机器可读版本。
- 所有名字、微信号、故事、日期和额度均为虚构数据。
- 正式后端仍需单独设计身份、权限、隐私、审计、删除和争议流程，不能直接把本数据文件当作数据库迁移方案。
- 动态流只保存对业务记录的引用和排序，不重复保存正文。

## 2. 数据关系

```text
member ──< circle_account >── circle
   │                              │
   ├──< listing >─────────────────┤
   ├──< good_card (from / to) >───┤
   └──< transaction (provider / receiver) >── circle

activity_reference ──> listing | good_card | transaction
```

## 3. 表结构

### 3.1 `members`

| 字段 | 含义 |
| --- | --- |
| `id` | 稳定成员 ID |
| `name` / `initial` | 展示名与头像角标 |
| `role` / `bio` | 社区角色与个人说明 |
| `color` / `avatar` | 头像颜色和造型变体 |
| `wechat` | 同圈成员点击联系后展示的虚构微信号 |
| `circleIds` | 加入的圈子 |

### 3.2 `circles`

保存圈子名称、货币名称、成员数、介绍、适用场景、加入方式、邀请说明、原则、规则、参考物和展示成员。三个圈子是同一产品中的三个实例。

### 3.3 `accounts`

每个成员在每个圈子拥有独立账户：`balance`、`given`、`received`。跨圈不合并、不兑换。

### 3.4 `listings`

统一保存“我想要 / 我可以给”。字段包括类型、标题、完整说明、可见圈子、可见范围、时间、地点、参考额度、标签、状态与创建时间。

### 3.5 `goodCards`

好人卡保存发卡人、接收人、完整故事、日期、标签、可见范围和发生圈子。它不保存金额，不改变账户余额。

### 3.6 `transactions`

交易保存圈子、提供者、接收者、额度、标题、完整故事、发生与记录日期、可见范围、确认状态和标签。

### 3.7 `activity`

综合动态的排序表，只保存 `source` 与 `sourceId`；页面再从对应业务表生成成员、圈子、正文和标签。

## 9. 页面如何使用这些数据

- 首页综合动态：`activity` 指向四张业务表中的记录，再生成动态卡片。
- 发现页：筛选 `listings` 中仍有效的需要与提供。
- 圈子页：读取 `circles`、当前用户在 `accounts` 中的圈内账户和圈子成员。
- 我的页面：读取俏也的完整好人卡、需要/提供、交易和各圈账户数量。
- 成员页：同一组件读取任意成员的公开好人卡、完整需要/提供、可见交易与各圈账户。
- 分享图：读取俏也当前仍有效的需要与提供，不单独维护一份分享文案。

## 10. 后端开发时仍需决定

- 真实 ID、微信授权与成员合并策略；
- 每种记录的读取、写入、隐藏、删除与导出权限；
- 神秘记录是否允许管理员看到当事人；
- 交易更正是否采用不可变事件账本；
- 账户汇总是实时计算还是保存缓存；
- 圈子退出、失联、拒绝和争议时的数据处理；
- 敏感信息最小化、保留期限与用户撤回机制。
