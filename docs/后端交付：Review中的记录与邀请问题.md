## 1. P0：拒绝 / 撤销记录必须对当事人留痕

### 当前问题

当 A 记录一笔互助给 B，B 拒绝后，A 的 `/bootstrap.records` 中不再包含该记录：测试中总写入 6 笔，但 bootstrap 只返回 5 笔 `confirmed` / `corrected` 记录，`rejected` 数为 0。

这违反产品承诺「拒绝或更正的原记录保留状态痕迹，但不进入正常公开交易流」。`redacted=true` 是可见性处理，不能成为把当事人记录从 bootstrap 删除的理由。

### 必须行为

1. `PATCH /records/:id {"action":"reject"}` 成功后，记录状态变为 `rejected`。
2. 提供者与接收者后续读取 `GET /bootstrap` 时，`records` 必须包含这条记录，至少返回现有 record contract 的字段：

   ```json
   {
     "id": "record-id",
     "circle_id": "circle-id",
     "provider_id": "member-a",
     "receiver_id": "member-b",
     "amount": 6,
     "title": "…",
     "story": "…",
     "visibility": "public",
     "status": "rejected",
     "created_by_id": "member-a",
     "pending_correction": null,
     "redacted": false,
     "recorded_at": "…"
   }
   ```

3. `rejected` 记录不得进入对第三方可见的 `activity` / 公共动态；非当事人也不得借此获取参与者或故事。
4. `redacted` 只表达隐私裁剪，不得覆盖 `status`。若记录本身是神秘 / 私密记录，仍按原有权限规则向当事人返回完整可审计的状态。
5. 若服务端已有撤销时间和执行者，请补充 `rejected_at`、`rejected_by_id`；这两个字段是建议项，当前前端不依赖它们。

### 验收

- `pending → rejected`、`confirmed → rejected`、`corrected → rejected` 均保留一条 `status=rejected` 的记录给 A 和 B。
- A、B 的常规动态都不出现该记录；A/B 的「互助记录」档案能显示“已撤销”。
- 同圈第三人和非同圈用户的 bootstrap 均不包含这条记录或其敏感字段。
- 重复拒绝返回幂等结果或明确的 4xx，不能重复冲销账户。
- 账户余额与 `given` / `received` 的冲销规则仍按现有账本问题单验收：[`后端问题：已更正记录撤销后余额未回滚.md`](后端问题：已更正记录撤销后余额未回滚.md)。

## 2. P0：通知必须区分更正提议，并带目标记录

### 当前问题

当 B 提议把一笔 10 的记录改为 6 时，后端发送：

```json
{"kind":"invite","amount":6,"note":""}
```

这与「新记录等待确认」复用了同一事件类型。当前前端已临时通过 bootstrap 中的 `pending_correction` 反查并渲染“更正提议”，但这种匹配依赖 actor、额度和当前未决状态，不能作为长期契约。

### 必须事件契约

新增或明确以下通知类型；所有可处理事件都必须携带 `record_id`：

```json
{
  "id": "notification-id",
  "kind": "correction_proposed",
  "record_id": "record-id",
  "actor_id": "member-b",
  "circle_id": "circle-id",
  "amount": 6,
  "note": "可选说明",
  "read": false,
  "created_at": "2026-09-30T00:00:00Z"
}
```

建议同时固定这些语义：

| `kind` | 含义 | 必填字段 |
|---|---|---|
| `record_confirmation_requested` | 新记录等待对方确认 | `record_id`, `actor_id`, `circle_id`, `amount` |
| `correction_proposed` | 对方提议变更额度，等待接受 / 谢绝 | `record_id`, `actor_id`, `circle_id`, `amount` |
| `record_rejected` | 原记录已撤销，不再需要处理 | `record_id`, `actor_id`, `circle_id` |
| `correction_resolved` | 更正被接受、谢绝或撤回 | `record_id`, `actor_id`, `circle_id` |

旧的 `kind=invite` 可以在一个明确的兼容期继续输出，但不能再用于新写入；兼容期内请至少补充 `record_id` 和可判别的 `text/event_type`。

### 验收

- 新记录待确认与更正提议分别产生不同 `kind`，前端无需按金额猜测。
- 每种记录通知均能凭 `record_id` 打开同一条交易。
- 同额、同一发起人并发的两笔交易不会串通知。
- 已处理记录的旧通知不再显示为“等待确认”。

## 3. P1：未登录邀请预览

### 新接口

```http
GET /invitations/:token/preview
```

这个接口由 loop-backend 提供；前端会增加同源代理后在 `/join/:token` 首屏调用。它**不得接受邀请、不得创建 membership / join request、不得消耗 token**。

### 成功响应

```json
{
  "status": "active",
  "circle": {
    "id": "circle-id",
    "name": "周末手作营地",
    "description": "一起做东西，也分享工具和时间。",
    "currency": "泡泡",
    "joining": "approval",
    "member_count": 12,
    "rules": ["可以开口，也可以拒绝"]
  },
  "inviter": {
    "display_name": "小满",
    "handle": "@xiaoman"
  },
  "expires_at": "2026-10-07T00:00:00Z"
}
```

### 隐私与安全

- 仅返回受邀人决定是否加入所需的公开元数据；不能返回 inviter 的联系方式、地址、邮箱、完整成员名单、账户余额或内部权限。
- token 是一次性随机凭证。失效、已使用或不存在时返回同一类泛化错误（建议 `410`），避免借响应差异枚举 token 状态。
- 响应设为 `Cache-Control: no-store`；token 使用后预览不能被 CDN / 浏览器缓存成仍可加入。
- 无需已登录 session；`POST /invitations/:token/accept` 的认证与单次使用行为保持不变。

### 验收

- 未登录访问有效邀请：首屏可见圈名、介绍、额度名、加入方式、成员数、约定摘要和邀请人显示名。
- `joining=direct` 与 `joining=approval` 均可预览，且预览不改变邀请可用性。
- 连续预览后首次接受成功；第二次接受仍按现有单次使用规则失败。
- 过期、已用、伪造 token 不泄露圈子或邀请人信息。

**2026-10-01 产品决定：不做邀请预览。** 维持现状——未登录用户点开邀请链接只看到登录表单，登录后自动加入。**后端不需要实现 `GET /invitations/:token/preview`**，本条关闭（非"修复"，是"决定不做"）。

## 7. BE05 幂等 并发与权限验收

本项是待证明的上线能力，不是已确认缺陷。请维护方提供集成测试或协助测试环境覆盖：

- 创建、确认、更正接受、撤销在响应丢失后重试不会重复记账。明确哪些操作天然幂等，哪些需要请求幂等键，以及键的作用域、有效期和冲突响应；前端不自行发明未支持的 header。
- 双方同时确认、撤销或处理同一更正时，最终状态合法且账户只变动一次。
- 相同邀请只能消费一次；审批和圈主转让以服务端当前权限判断，旧权限不能继续生效。
- 非成员、待审批成员、同圈第三人和其他圈成员不得读取不属于其权限的身份、联系方式、记录和余额，也不能凭对象 ID 修改它们。
- 私密、神秘、公开三类记录和跨圈发布的实际 API 返回符合产品约定；权限过滤必须在服务端完成。

验收需标明测试版本、身份角色、状态转换和前后账户值。生产只做自己创建对象的正常频率小样本；并发压测与事务失败注入等待隔离后端环境。

## 8. BE06 OTP 与会话可靠性
