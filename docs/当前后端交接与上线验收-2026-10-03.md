以下路径没有 `/api` 前缀的是后端路径；现有前端代理另行标出。“建议”路径是待双方确认的提案，不能当作已上线接口。后端须交付 OpenAPI 或等价请求/响应样例、权限表、错误码、版本和清空交付说明。身份从 session 推导，不能相信客户端传入的 viewer 或 owner 身份。

- 现有 `POST /circles`：前端新圈固定 `joining=approval`、`allow_negative_balance=true`、`require_confirmation=false`、`allow_reject_correct=true`。

### H02 · 双人修改与撤销、修订历史（P1）

- 现有 `PATCH /records/:id {action:"correct", amount, title, story}` 与 `POST /records/:id/correction {action:"accept"|"decline"|"withdraw"}`：确认文案单独修改、金额不变也能形成提议；返回完整待决内容与发起人。

- 可见范围改变也需另一方明确同意；从私密转公开时双方能预览将公开内容。非当事人不能读到隐藏正文、待决私密版本或完整历史。

### H09 · 按成员导入社区已有积分（P1，正式社区接入前）

这是用户确认的新需求：**由平台管理员本人使用本地运行的 admin 页面，圈主暂不拥有发放权限。** 圈主先创建圈子，用户完成注册并加入该圈；圈主联系平台管理员，管理员登录后台，选择圈子、逐人填写初始积分、预览并确认发放。“统一发放”指由平台管理员集中操作，成员金额仍可不同。**本仓库已实现`/admin`页面与独立同源管理员代理；真实管理员后端尚未交付。** 本地运行方式、实际采用的`/admin/...`后端路径与请求/响应格式见[管理员后台契约](管理员后台：本地运行与接口契约.md)。下方早期建议路径以该精确契约为准；已有实现不代表真实后端已验收。

**页面范围**：独立管理员登录页（密码登录，首次开通和重置由维护方提供）、圈子搜索/选择、圈内成员列表、每人初始积分输入、来源/基准日期/备注、发放前预览（人数、总额、逐人金额）、确认发放、结果与历史批次查询、退出登录。显示当前余额、已发放的期初金额和本次变更；已经初始化的成员标明不可再次发放。用户只注册但未加入该圈时不能给其圈子账户发放；后台明确提示先完成入圈，不自动替用户加入。

**登录与调用**：管理员密码由服务端验证并安全存储，不在页面代码中写死、不靠前端对比密码放行，也不把数据库凭据或后端管理密钥放入浏览器。服务端建立可过期、可退出的管理员会话；每个管理员读取/写入接口都验证平台管理员身份。页面通过同源管理员代理调用后端管理API，服务器处理服务凭据；生产普通成员、圈主即使直接请求接口也不得发放。提供密码错误限流、会话失效、退出及密码重置流程。具体后台路径和部署方式由前后端约定，优先保持现有同源代理架构。

**业务语义**：每人在指定圈子有各自的期初余额，例如A为300分、B为80分；没有导入的成员默认0。期初积分是独立账本来源，不伪装成双方互助，不增加given/received或有效互助笔数。后续余额等于期初积分加上正式互助的净变化。期初总额不必为零，后端须记录并对账该批次总额，不创建虚构负余额成员凑平。

以下为建议契约，路径和字段名须由后端确认：

- `POST /admin/session`、`GET /admin/session`、`DELETE /admin/session`：密码登录、读取管理员登录状态、退出。管理员身份独立于圈主角色；认证凭据不出现在普通bootstrap中。
- `GET /admin/circles`、`GET /admin/circles/:id/members`：后台搜索已有圈子并列出真实成员，返回稳定account_id、显示资料、当前余额、期初积分及是否已初始化；支持分页。该受控列表可包含非公开圈，不改变普通发现页权限。

- `POST /circles/:id/opening-balance-imports/preview`：提交批次键、来源说明、积分基准日期及成员/积分列表；仅校验和预览，不改余额。返回明确的匹配成员、当前余额、拟导入期初积分、导入后余额、错误行、总人数和总积分，并签发绑定数据与当前版本的预览ID。
- `POST /circles/:id/opening-balance-imports/:preview_id/confirm`：授权操作者确认后一次性写入；服务端验证预览未过期、未改动、成员与账户版本仍一致。相同幂等键/预览重复提交返回同一批次结果，不重复加分。并发导入同一成员只能成功一次。
- `GET /circles/:id/opening-balance-imports/:batch_id`：授权读取批次状态、逐人结果与审计信息；返回结果可供导出和复核。bootstrap/成员账户须返回实际余额，建议另提供opening_balance供核对。

```json
}
```

**权限与校验**：本轮只为平台管理员开通导入权限，圈主与普通成员均无权限；身份来自管理员认证会话。操作者只能写入授权圈子。按稳定account_id匹配已加入成员；若使用邮箱/外部编号导入，提供明确匹配步骤，不按显示姓名猜测、不自动创建错误身份。重复成员、非成员、无效ID、非整数、超出允许范围、批次大小超限须报明确错误。负期初积分按当前允许负余额的规则支持，数值范围由后端契约明确。导入接口虽然示例使用圈子资源路径，仍必须执行管理员授权，或由后端统一放入/admin命名空间。

**写入与纠错**：每个成员圈子账户只能初始化期初积分一次，不能用重复发放来覆盖余额。服务器锁定账户并校验预览版本；按独立期初账本项入账，即使注册后已有互助，也保留其净变化，不能把余额直接赋值为输入积分。校验失败整批不写入，确认成功整批事务提交。录错需提供受控的冲正/修正操作与留痕，保留原批次、调整理由、操作者与时间，不能删除审计或重置已有互助；修正不能伪装为第二次期初发放。其余日常增发不在本轮需求中。

**交付要求**：后端交付管理员密码认证、角色授权、圈子/成员查询、期初发放/批次/纠错接口及样例、管理员开通与密码重置方式、真实测试环境；具体响应必须与已实现页面契约对齐，含分页与按preview_id查询未知结果。前端页面与代理已完成，待连接真实管理API联合验收；CSV可补充，不能代替页面。保存来源、基准日期、操作人、服务端时间、批次ID、每个成员的期初值和变更前后余额。清空后的用户ID需重新匹配，不能沿用测试批次ID。

**验收**：管理员密码登录，选圈逐人填写A=300、B=80，C未导入为0；预览账本不变，确认后刷新/重新登录回读一致，given/received与互助数仍为0。A帮助B记10后余额310/70，互助双方同意撤销后恢复300/80。再用未初始化但已有互助净变化的成员验证期初发放不覆盖原账。重复/并发确认不再次加分；圈主和普通成员直接调用发放/查询接口被拒；未入圈、错误成员、陈旧预览均拒绝且无部分写入。退出或会话到期后不能继续管理；纠错有完整审计。
