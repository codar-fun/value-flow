# 后端交接：互助记录与发布修改

日期：2026-10-03。以下是本轮产品决定和待确认的后端契约，**不代表 `loop-backend` 已实现或部署**。前端目前只把已支持的金额、标题、说明更正做成提议；其余能力不得靠本地状态假装成功。

## 产品规则

1. 新互助记录由任意当事人发布后立即入账，并通知另一方；不再要求首次入账前逐条确认。旧圈的待确认记录需有明确迁移规则。
2. 提供者和接受者都可以发起修改，与最初由谁记录无关。修改在另一方同意前不生效；对方拒绝则原记录保持有效。
3. 修改范围包括金额、标题／事情经过、可见范围，以及整笔记录的撤销。撤销也视为一项需对方同意的修改；不能把现有立即生效的 `reject` 接口包装成“申请撤销”。
4. 自己发布的「我想要／我可以给」由发布者自行编辑内容、参考额度、可见范围和展示状态，无需另一人确认。「暂时隐藏」表示从其他人可见的列表撤下，恢复展示后重新可见；它不等于删除。
5. 每次发布、提议、同意、拒绝、撤回和生效都保留时间、操作者与变更前后内容。当事人能查看记录历史；其他人只能看到其权限允许的当前版本和必要状态。

## 现有接口与缺口

- `PATCH /records/:id {action:"correct", amount, title, story}` 现由前端转发；后端需确认**只改标题或说明而金额不变**也能形成待对方同意的提议，并返回完整提议内容。`POST /records/:id/correction` 已提供接受、谢绝、撤回动作。
- 当前 `PATCH /records/:id {action:"reject"}` 会立即撤销。需要新的双人撤销提议与确认语义，原接口的兼容和迁移方式须明确。
- 记录可见范围目前没有修改契约。后端须在修改生效时重新执行服务端权限过滤；从私密改公开前应让双方看到将公开的内容。
- 前端现已提供「编辑内容」表单：提交 `title`、`detail`、`reference`、`visibility`、`circle_ids` 到 `PATCH /listings/:id`，并在重新读取 bootstrap 后逐项核对结果。现有后端只确认过 `status=active|paused|closed`，因此线上编辑能力仍待后端实现／确认；不能把本地 UI fixture 的成功视为线上成功。服务端须只允许发布者编辑，并返回或持久化完整更新后的发布。
- 当前 bootstrap 只有记录／发布的创建日期和单个待决更正，没有完整修改时间、历史版本或撤销提议。需要由服务端返回可授权读取的修订事件或历史摘要；前端不能用浏览器时间补造。
- 现有圈子仍可能关闭 `allow_reject_correct` 或开启 `require_confirmation`。统一规则对旧圈何时生效、待处理记录如何处理，需要后端迁移方案。

## 验收

使用独立 A、B、C 账号验证：A 记一笔后立即入账；A 和 B 均能分别发起金额／文案／可见范围修改；提议未获同意前双方账本和公开内容不变；对方同意后一次性更新，拒绝后原版本不变；双方同意撤销后余额按当前有效金额完整回滚。B 无权改 A 的需要／提供，A 可自行编辑和暂时隐藏，C 只能看到当前允许公开的版本。并发、重试、私密记录及完整时间线也须回归。
