# 后端交接：档案与圈子发现权限

日期：2026-10-03。前端已用 `tests/ui-preview.mjs` 的虚构数据制作档案与入圈前预览；本文是后端契约提案和验收要求，**不代表 loop-backend 已提供或部署这些能力**。

## 产品规则

1. 自己的档案可按自己加入的圈子查看需要、提供、好人卡、互助记录和账户值。本人能处理自己有权限确认、更正或撤销的记录。
2. 他人档案顶部的「全部共同圈／圈子」仅包含查看者与此人共同加入的圈子。选择一个圈子后，只返回查看者在该圈有权看到的内容。
3. 他人档案另列此人加入、查看者未加入的圈子。查看者能看到圈子名称、介绍、加入方式和自己的申请状态，并能进入加入前的圈子介绍；不能由此看到此人在该圈的个人档案、余额、圈内互助记录或成员联系方式。
4. 从「发现」或他人档案进入未加入圈子时，先看圈子介绍，再由用户主动申请／加入。申请状态由后端决定；等待审批时不得重复申请，可以撤回。

## 当前前端能拿到什么

- `GET /bootstrap` 提供当前用户世界中的成员、圈子、账户、记录和发布内容。`db/runtime.ts` 从已返回圈子的 `member_ids` 推导 `Member.circleIds`。这不能可靠列出某人加入、但查看者未加入的圈子。
- `GET /api/circles` 转发 loop 的圈子列表，前端只保留当前用户未加入的互助圈。它没有「这些圈子中哪些属于指定成员」的关系。
- 现有 `DiscoverableCircle` 含名称、一句话介绍、加入方式和人数；完整介绍与圈子约定目前只在 UI fixture 中造数据。
- `POST /api/circles/:id/join` 和撤回路由已有，前端应继续使用后端返回的 `active` / `pending` 状态，不自行推断审批结果。

## 需要后端确认和提供的读取能力

具体路径可与后端维护方协商；以下是返回语义，不要求照抄字段名。

### 查看者视角的成员档案

按 `viewer_id` 与 `member_id` 返回：

- 成员基础资料及允许查看的联系方式；
- `shared_circles`：双方共同圈子，包含圈子 ID 与名称；
- `other_discoverable_circles`：此人加入而查看者未加入的圈子，仅包含圈子 ID、名称、简短介绍和查看者的加入状态；
- 共同圈范围内可见的需要／提供、好人卡、互助记录及允许展示的账户值。

过滤应在服务端完成。不能将非共同圈的账户和私密记录发给前端，再依赖 UI 隐藏。私人／神秘记录仍遵守现有当事人和脱敏规则；待确认与更正提议仅向有权处理或查看的当事人返回。列表数量与实际可见内容的口径一致，已撤销记录如对当事人保留，要明确标注且不计入有效互助数。

### 未加入圈子的访客介绍

按圈子 ID 返回非成员可读的：名称、图标、完整介绍、圈子约定、成员人数、加入方式、查看者申请状态。不得包含成员列表、个人余额、圈内记录、成员联系方式。若某圈不允许从发现入口申请，需返回明确的不可申请状态与说明，不应让前端靠 `joining` 字段猜测。

## 验收场景

使用独立 A、B、C 身份及至少三个圈子：A/B 共同圈、B 独有圈、A 独有圈。

1. A 看 B 档案：顶部只有 A/B 共同圈；B 独有圈出现在「其他圈子」，可看介绍，不可获取 B 在该圈的余额和记录。
2. A 直接请求 B 独有圈的档案／账户／记录接口：后端仍拒绝或只返回访客可读字段。
3. A 在发现页和 B 档案打开同一圈子的访客介绍，内容与申请状态一致；阅读本身不创建申请。
4. A 申请需审批圈后状态为 `pending`，重复提交不产生第二份申请，撤回后状态恢复；被批准后才可看到成员态内容。
5. A 在共同圈切换档案范围，返回的内容、统计及权限一致。私人、神秘、待确认、更正、撤销记录分别按当事人／第三方验证。

前端 fixture 可验证布局和点击路径，不能关闭以上后端验收项。
