# P1：已更正的互助记录撤销后，记录消失但双方余额未回滚

## 一句话说明

一笔已经确认入账、之后又由另一方接受更正的互助记录，在执行撤销后，接口返回成功，记录也从列表中消失，但提供者和接收者的账户余额、累计给出和累计收到均没有回滚。

这会造成“可见记录”和“真实余额”互相矛盾，属于账本一致性问题，建议按 P1 处理。

## 测试环境

- 测试日期：2026-08-21
- 前端分支：`codex/value-flow-sync`
- 前端：本地 `http://localhost:3000`
- 后端：生产 `https://loop-api.sola.day/api`
- User A：`@ciaoye`（流程测试员），测试期间已由圈主转为普通成员
- User B：`@test3`，测试期间接任“流程测试圈”圈主
- 圈子：流程测试圈
- 额度名称：测试额度
- 测试记录标题：`站内弹窗回归测试`
- 测试记录 ID：`75f10b1a-97d7-425c-bf30-9f7f97be23cb`

圈主转让发生在本轮其他测试中。该问题的主体是互助双方账户和记录状态，并不依赖当前谁是圈主。

## 完整复现步骤

1. User B 创建一笔互助记录：User A 帮助 User B，额度为 4。
2. 记录进入待确认状态，双方余额仍为 0。
3. User A 确认入账。
4. 刷新双方页面：User A 为 `+4` / 累计给出 4；User B 为 `-4` / 累计收到 4。
5. User A 提议把额度从 4 更正为 6。
6. User B 接受更正。
7. 刷新双方页面：User A 为 `+6`，User B 为 `-6`；记录状态为 `corrected`。
8. User A 撤销这笔已更正记录。
9. 撤销请求返回 HTTP 200。
10. 刷新 A、B 两个独立会话并重新读取 bootstrap。

## 预期结果

- 记录变为 `rejected` / 已撤销，不再计入有效动态；
- User A 余额、累计给出恢复为 0；
- User B 余额、累计收到恢复为 0；
- 状态更新和两个账户冲销在同一个数据库事务中完成；
- 任一环节失败则整体回滚；重复请求不发生二次冲销。

## 实际结果

- 撤销接口返回成功；
- 记录从双方动态和互助档案中消失；
- User A 刷新后仍为 `+6` / 累计给出 6；
- User B 刷新后仍为 `-6` / 累计收到 6；
- 两个独立会话结果一致，不是单页缓存；
- 用户已经看不到有效记录，却留下无法解释的 6 点余额。

## 前端调用与责任边界

前端没有根据可见记录计算余额。它直接展示 loop-backend `/bootstrap` 返回的 `circle_accounts.balance`、`given`、`received`。

前端调用：

```http
PATCH /api/transactions/75f10b1a-97d7-425c-bf30-9f7f97be23cb
Content-Type: application/json

{"action":"reject"}
```

同源代理继续调用 loop-backend：

```http
PATCH /api/records/75f10b1a-97d7-425c-bf30-9f7f97be23cb
Content-Type: application/json

{"action":"reject"}
```

请求返回 HTTP 200，随后记录确实消失，说明后端接受并执行了状态变更。前端不能通过本地重算余额掩盖后端账本不一致。

## 已排除

### 不是所有撤销都失效

另一笔没有经过更正的 5 点记录走 `pending → confirmed → rejected`，撤销后双方余额正确恢复为 0。

### 不是按旧金额 4 错误回滚

如果按旧金额回滚，`+6/-6` 应变成 `+2/-2`。实际余额完全不变，因此更像是冲销分支没有运行。

## 高概率根因

请重点检查撤销逻辑是否只把 `confirmed` 识别为已入账状态。更正被接受后状态变为 `corrected`；如果它没有被归类为 posted / 已入账状态，撤销就可能只更新记录状态而跳过账户冲销。

还需检查：

1. 冲销是否读取当前有效金额 6，而不是原金额 4；
2. 更正接受时是否把原值和当前值分散在不同字段，撤销读取了错误字段；
3. 状态更新与账户更新是否处于同一个 `Ecto.Multi` / 数据库事务；
4. 重复撤销、超时重试是否幂等；
5. `given` / `received` 是否和 `balance` 使用同一套 delta。

## 建议修复

建立明确的“已入账状态”判断，至少包含 `confirmed` 和 `corrected`。撤销时从记录的当前有效版本获得 provider、receiver 和 amount，在同一个事务中：

1. 锁定记录和两个账户；
2. 验证记录尚未被撤销；
3. 按当前有效金额反向更新双方 `balance`、`given`、`received`；
4. 更新记录状态和审计字段；
5. 提交事务；任一失败则整体回滚。

如果账本使用不可变流水，优先追加 reversal entries，而不是直接覆盖旧流水。

## 必需回归测试

1. `pending → confirmed → rejected`：按确认金额完整回滚；
2. `pending → confirmed(4) → corrected(6) → rejected`：按 6 完整回滚；
3. 更正到更小金额后撤销：按当前有效金额完整回滚；
4. 重复撤销同一记录：不能重复冲销；
5. 事务中任一账户更新失败：记录状态与双方账户全部不变；
6. A、B 分别读取 bootstrap：记录状态和账户数值一致；
7. `balance`、`given`、`received` 三个字段同步回滚。
