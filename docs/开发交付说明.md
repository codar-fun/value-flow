# 流动圈静态 Demo：开发交付说明

> 状态：当前静态页面的工程与功能事实总览
> 日期：2026-07-15
> 适用对象：接手正式产品开发的产品、设计、前端、后端与测试人员
> 线上版本：<https://liudong-circle-demo.helloworld-zoey.chatgpt.site>

## 1. 先说结论

当前交付物是一套**移动端优先、桌面端有扩展世界面板的静态交互 Demo**。它已经比较完整地表达产品对象、页面层级、核心语言、演示数据和主要操作路径，但它不是可直接上线的业务系统。

开发接手时应把三层内容分开：

1. **产品要求**：以 [`产品需求文档：运营流程.md`](产品需求文档：运营流程.md) 为准；
2. **当前演示行为**：以本文件、`app/page.tsx`、`app/demo-data.ts` 和 `app/globals.css` 为准；
3. **正式技术方案**：目前尚未设计，不能从静态组件状态或虚构数据结构直接推断。

最重要的产品边界是：

- 圈内互助额度是 mutual credit 账户记录；
- 好人卡是没有金额、不能兑换、不产生债务的认可故事；
- “需要 / 提供”是发布内容，发布本身不改变余额；
- 免费分享和不记录的善意始终可以存在；
- 不与人民币兑换，不做信用分、贡献榜和跨圈汇率；
- 现实协商继续发生在微信或线下，产品不做站内聊天和履约平台。

## 3. 当前工程是什么

### 3.1 技术栈

- Next.js 16 App Router；
- React 19；
- TypeScript；
- Vinext + Vite 构建；
- Cloudflare Worker 运行入口；
- OpenAI Sites 托管；
- ESLint 与 Node Test 做基础检查；
- Drizzle 和 D1 只有空脚手架，当前没有真实表和数据库绑定。

### 3.2 当前只有一个页面路由

当前只有 `/`。所谓“关于流动圈”“创建新圈子”“发现”“圈子”“我的”都不是独立 URL，而是 `Home` 组件内部的 `view` 状态：

```ts
type View = "feed" | "discover" | "circle" | "me" | "about" | "create";
```

弹层也由一个联合状态控制：

```ts
type Overlay =
  | "share"
  | "profile"
  | "intro"
  | "rules"
  | "members"
  | "invite"
  | "feedFilter"
  | "post"
  | "settings"
  | null;
```

因此刷新页面会回到默认综合动态，浏览器地址不能深链到某个圈子、成员或弹层。正式开发应决定哪些状态成为独立路由、哪些继续保留为弹层。

### 3.3 关键文件

| 文件 | 当前职责 |
| --- | --- |
| `app/page.tsx` | 全部视图、弹层、交互状态和静态业务映射 |
| `app/demo-data.ts` | 唯一运行中的虚构业务数据源 |
| `app/globals.css` | 全部设计 token、组件样式和响应式规则 |
| `app/layout.tsx` | 页面标题、说明、favicon 和社交分享元数据 |

| `tests/rendered-html.test.mjs` | 构建产物渲染与关键产品语言的基础回归检查 |

## 4. 页面导航与状态逻辑

### 4.1 两个容易混淆的圈子状态

页面故意保留两个不同状态：

- `circleId`：当前业务上下文，用于圈子页、规则、成员、个人档案中的圈内账户以及右侧参考物；
- `feedCircleId`：首页动态范围，可以是具体圈子，也可以是 `all`。

`selectCircle(id)` 会同时更新两者，并默认返回动态页；从概念页或“我的圈子”进入圈子详情时，会显式传入 `nextView = "circle"`。

`showAllCircles()` 只把动态范围设为 `all`，不会清空 `circleId`。所以“全部圈子动态”状态下，桌面右侧参考物仍展示最近一次选中的圈子；初始为俏也交换圈。这是当前 Demo 的设计，不应误解为跨圈统一参考物。

### 4.2 顶部与底部导航

- 桌面左上角品牌标识、手机顶栏“流”图标：进入整体概念页；
- 手机顶栏头像：进入“我的”；
- 底部导航：动态、发现、统一发布入口、圈子、我的；
- “圈子”按钮进入当前 `circleId`；
- 概念页和创建页保留底部导航，但隐藏圈子切换条。

## 5. 当前完整功能地图

### 5.1 综合动态 `feed`

入口：默认首页、底部“动态”、桌面“全部圈子动态”或任一圈子卡。

当前行为：

- 展示泡泡助手与“说一句”入口；
- 在全部圈子和单圈范围之间切换；
- 展示已加入圈子、给出过、好人卡三个概览；
- 支持全部、互助记录、需要、提供、好人卡五种筛选；
- 点击人物进入成员档案；
- 点击正文或“详情”打开动态详情；
- 点击分享打开俏也的分享图预览。

重要实现限制：动态不是从全部业务表自动生成，而是只读取 `demoDb.activity` 中策展的 7 条引用。

### 5.2 发现 `discover`

- 支持全部、需要、提供、附近四种筛选；
- “附近”使用数据里的手工布尔字段 `nearby`，没有定位能力；
- 当前列表仍来自 7 条策展动态中的需要/提供，不是全部 15 条 `listings`；
- “＋ 发布”直接以“我想要”意图打开统一发布弹层。

### 5.3 圈子页 `circle`

- 展示当前圈子的名称、地点、角色、货币与本人余额；
- 可打开说一句、邀请成员、圈子介绍；
- 展示给出/收到、参考物、最近活跃成员和该圈策展动态；
- 点击参考物进入规则；
- 点击“全部成员”打开成员地图；
- 点击成员进入完整档案。

三个示例圈只是同一产品的三个实例：俏也交换圈、做人共学、龙潭生活营地。

### 5.4 整体概念页 `about`

- 解释产品一句话定义；
- 分开解释圈子、互助额度、需要/提供、好人卡；
- 展示一次互助从线下/微信到确认记录的三步流程；
- 三张圈子卡读取真实演示数据并进入对应圈子；
- 展示不兑换、不排名、可拒绝、可退出和敏感互助可不记录等边界；
- 可返回动态或进入创建圈子。

### 5.5 创建圈子 `create`

这是应用内四步页面，不是弹层：

1. **圈子身份**：名称、地图简称、互助额度名称、一句话介绍、熟人/共学/线下场景；
2. **互助设置**：固定为 mutual credit 账户，设置第一项参考物，并选择是否允许需要/提供与好人卡；
3. **成员与边界**：受邀直入或管理员审批、圈内公开或仅当事人、神秘记录、退出规则；
4. **预览确认**：所有选择实时进入圈子预览。

保存后只展示“草稿已保存”的静态完成状态。它不会把新圈写入 `demoDb`，不会出现在圈子列表，也不会创建账户或邀请链接。组件离开或刷新后状态丢失。

### 5.6 我的 `me`

- 展示俏也的跨圈角色卡和好人卡故事；
- 三个档案入口分别打开好人卡、需要/提供、互助记录；
- 展示当前需要和提供；
- 公开设置打开本地开关弹层；
- 展示三个圈子及各自余额；
- 可进入创建圈子。

### 5.7 成员完整档案 `profile`

三个标签：

1. 好人卡：发卡人、故事、日期、圈子、标签；
2. 需要/提供：完整说明、时间、地点、参考、可见范围和状态；
3. 互助记录：双方、额度、圈子、日期、可见范围和确认/更正/撤销状态。

可见性模拟规则：

- 本人固定为 `qiaoye`，能看到自己的全部交易状态，包括私密和撤销；
- 查看其他成员时，只显示 `visibility === "public"` 的交易；
- 好人卡只显示跨圈公开卡，本人可额外看到隐藏卡；
- 需要/提供当前没有按查看者过滤，档案会显示该成员全部 listing；这是静态简化，不是正式权限要求；
- 点击联系后直接展示虚构微信号，复制只显示提示。

### 5.8 说一句 `composer`

支持四种意图：记一笔、我想要、我可以给、好人卡。

交互过程：

1. 选择意图；
2. 查看预设语音文案，或切换键盘输入；
3. 点击整理，进入固定草稿；
4. 选择可见范围；
5. 确认发布。

所有草稿正文都是 `draftCopy` 中的固定示例。输入框内容不会被解析，选择的可见范围也不会写入数据。确认后关闭弹层并显示 toast，不改变余额、列表或档案。

### 5.9 圈子介绍、规则、成员与邀请

- 圈子介绍：为什么存在、适合谁、营地约定、加入方式；
- 规则：圈子规则、参考物和敏感信息边界；
- 全部成员：只展示 `memberIds` 中的 5 个演示角色；圈子卡上的 18/32/24 是世界观总人数，不代表全部都有完整虚构档案；
- 邀请：邀请链接与微信邀请图两个标签；复制、发微信、保存图片都只是提示，不调用真实系统能力。

### 5.10 分享图、详情与公开设置

- 动态详情根据来源展示 listing、transaction 或 good card 的不同字段；
- 分享图目前无论从哪条动态进入，都展示俏也当前有效的需要和提供，不展示被点击动态的作者；
- 二维码是装饰网格，不是可扫描码；
- 公开设置中的三个开关只在弹层打开期间有效，保存后不会改变页面内容。

## 6. 数据事实与静态策展层

### 6.1 完整虚构数据库规模

| 数据 | 数量 |
| --- | ---: |
| 成员 | 9 |
| 圈子 | 3 |
| 圈内账户 | 16 |
| 需要/提供 | 15 |
| 好人卡 | 12 |
| 互助交易 | 9 |
| 首页动态引用 | 7 |

### 6.2 为什么完整数据多于首页内容

`demoDb.activity` 是静态页面的策展与排序层，只引用：

- 4 条需要/提供；
- 2 条交易，其中 1 条是神秘记录；
- 1 张好人卡。

完整数据主要在成员档案、“我的”和圈子资料里出现。正式后端不应照搬这个固定数组；应根据记录状态、可见范围、成员关系和发布时间生成动态流。

### 6.3 当前跨圈 listing 的简化

`listings.circleIds` 可以有多个圈，但 `buildPosts()` 为动态卡只取 `circleIds[0]` 作为 `circleId`。因此当前单圈动态筛选不会把一条跨圈 listing 同时放进所有相关圈。这是演示层的已知简化，正式实现应使用多圈关联表或可见性查询，而不是复制正文或只取第一个圈。

## 7. 产品要求与静态演示行为的区别

| 主题 | 正式产品要求 | 当前静态 Demo |
| --- | --- | --- |
| 登录与身份 | 微信/真实身份方案待设计 | 固定当前用户 `qiaoye` |
| 数据保存 | 需要真实持久化、权限和审计 | React 本地状态 + TypeScript 常量 |
| 语音/截图 | Agent 识别并生成草稿 | 固定示例句和固定草稿 |
| 交易确认 | 一方确认先入账，另一方可修改或拒绝 | 只显示成功提示，不入账 |
| 更正/撤销 | 影响余额并保留状态历史 | 只用虚构交易展示已有状态 |
| 发布需要/提供 | 写入记录并按范围分发 | 不新增列表 |
| 发好人卡 | 写入接收者档案，可隐藏 | 不新增卡片 |
| 创建圈子 | 创建圈、成员规则、账户与邀请 | 只保留到完成预览 |
| 联系成员 | 校验同圈关系后展示联系方式 | 点击即展示虚构微信号 |
| 分享 | 生成真实图片和可扫描入口 | 页面内视觉预览 |
| 权限 | 服务端强制执行 | 组件内条件过滤，不能视为安全机制 |
| 路由 | 应支持可分享和可恢复的页面状态 | 单路由、刷新复位 |

## 8. 当前已确认、不要从旧文档误实现的决定

1. 第一版不做付费购买初始币、预付权益、提现、投资或升值承诺；
2. 不做不同圈子额度之间的兑换；
3. 不做持有税、过期惩罚或连续签到；
4. 不做人员信用分、贡献排名和公开余额榜；
5. 交易记录采用“一方确认先入账、另一方可事后修改或拒绝”，不是必须双方先确认；
6. 进入圈内动态的展示档位是圈内公开和神秘记录；仅当事人记录可以存在，但不进入公共动态；
7. 好人卡不能花、不能转为额度、没有金额；
8. “我想要 / 我可以给”不代表承诺接单，任何人可无理由拒绝；
9. 参考物只是协商参考，不是统一价格；
10. 三个演示圈子不是产品分类，也不是固定模板。

## 9. 正式开发前必须补的技术设计

静态 Demo 没有替开发团队做以下决定：

- 用户、微信身份、重复账号和成员邀请的真实模型；
- 圈子、角色、管理员和成员权限矩阵；
- listing 的多圈关联、跨圈公开和失效机制；
- good card 的隐藏、删除、举报和接收者控制；
- transaction 的不可变事件、余额汇总、更正、拒绝和并发一致性；
- 神秘记录对普通成员、管理员、平台和当事人的不同可见性；
- 个人信息告知、同意、导出、删除、保留期和泄露响应；
- 圈子暂停、退出、失联和负余额如何处理；
- Agent 输入的隐私边界、人工检查和错误恢复；
- 图片、二维码、微信分享和小程序/网页之间的真实跳转；
- 监控、日志、备份、迁移、测试数据和运营后台。

建议正式实现至少拆出：

- 领域层：`Circle`、`Membership`、`CircleAccount`、`Listing`、`GoodCard`、`TransactionEvent`、`Invitation`；
- 权限层：本人、同圈成员、圈管理员、平台运营四类读取/写入策略；
- 查询层：综合动态、单圈动态、发现页、个人档案、圈子档案；
- 工作流：记录互助、确认/拒绝/更正、发布 listing、发卡、邀请/审批、退出/导出；
- 展示层：把当前单文件组件拆为路由页面和复用组件。

这些只是拆分边界，不是已经确认的数据库表或 API 设计。

## 10. 推荐的开发拆分顺序

1. 先冻结产品对象与权限矩阵；
2. 设计数据库和不可变交易事件，验证余额守恒与更正；
3. 实现身份、圈子、成员和邀请；
4. 实现只读页面与动态查询；
5. 实现需要/提供与好人卡写入；
6. 实现互助记录、拒绝和更正；
7. 接入分享、微信和 Agent 输入；
8. 最后再做运营后台、统计和扩展机制。

不要从“把静态页面接上数据库”开始。权限、事件历史和可见性若没有先设计，后续很容易把隐私与账本逻辑写死在前端。

## 11. 本地运行与检查

环境：Node.js 22.13 或更新版本，包管理器使用 pnpm。

```bash
pnpm install
pnpm dev
```

交付前执行：

```bash
pnpm lint
pnpm test
```

`pnpm test` 会先构建，再启动 Node 测试读取构建产物，检查页面 shell、关键产品语言、数据文件和设计语言仍然存在。
